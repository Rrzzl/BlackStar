================================================================================
 1. THE GAME
================================================================================

Black Star is a 2D game with two halves stitched into one shell.

  • SPACE (built)    — top-down dogfight combat, trade, exploration between
                       stations and planets. Seeded procedural sector. You pilot
                       a ship, fight enemies, dock, trade, save, die.
  • PLANET (rebuilding) — side-scrolling metroidvania in the Blasphemous /
                       Hollow Knight lineage. Hand-crafted rooms, gravity +
                       jump + melee, gothic-alien ruin tone, souls-like
                       difficulty. Was originally a top-down procedural dungeon
                       — pivoted away from that in M3a.

Scope is AAA ambition on indie execution — systemic depth, legacy mechanics,
Decay Clock as long-term pressure, Black Star as a scripted multi-year event.
The production brief is "treat this like a studio, not a weekend prototype."

Loop (target):
  1. In space: fight, trade, earn credits, upgrade.
  2. Land on planets: descend into ruins, explore, fight, recover lore/loot.
  3. Die: permadeath with legacy — estate passes to the next captain.
  4. Over time: Decay Clock degrades the galaxy; the Black Star event fires
     and reshapes the map. Your legacy is how you prepared for it.

Only #1 and the shell of #2 are built as of m3a-complete.


================================================================================
 2. TECH STACK
================================================================================

  • TypeScript (strict: noUncheckedIndexedAccess, exactOptionalPropertyTypes)
  • Vite 5 for dev server + production build
  • Canvas 2D — no WebGL, no shaders, no Three.js. Internal resolution 640×360.
  • Vitest for unit tests. No Playwright, no Cypress.
  • ESLint with a zero-warning policy.
  • No runtime dependencies except what ships in-browser. No Node server.
  • Save format: JSON in localStorage, versioned, migrated forward on load.

Commands (run from project root):

  npm run dev       Vite dev server on http://localhost:5173/
  npm run typecheck tsc --noEmit
  npm run lint      ESLint over src and tests
  npm run test:run  Vitest one-shot
  npm run build     typecheck + Vite build

Path aliases (configured in both tsconfig.json and vite.config.ts):

  @engine/   core engine services (GameLoop, Scene, Input, Renderer, Save ...)
  @core/     pure-logic game subsystems (economy, combat, platformer, RNG ...)
  @scenes/   scene classes (SpaceScene, PlanetScene, TitleScene ...)
  @ui/       UI primitives (Label, Button, Panel, Bar, List ...)
  @content/  JSON content (hulls, modules, weapons, rooms, .tmj.json files)

================================================================================
 5. NON-NEGOTIABLE RULES (violating any of these breaks the architecture)
================================================================================

ARCHITECTURE

  • Layering invariant: src/core/ NEVER imports from @engine/, @scenes/,
    or @ui/. Verify with:
        grep -rn "@engine\|@scenes\|@ui" src/core
    Must be empty.

  • Strict TS: noUncheckedIndexedAccess + exactOptionalPropertyTypes.
    Array accesses need `!` or null-checks. Optional properties are not
    "allowed undefined" — you must be explicit.

  • Seeded RNG only in authoritative paths. Math.random() is banned in
    src/core/ and all gameplay paths. Cosmetic jitter (camera shake) is
    the only allowed exception.

  • Save format is versioned. Every schema change requires a v(n)→v(n+1)
    migration and updates to Save.test.ts, SaveSnapshot.test.ts, and
    SaveSnapshotMigration.test.ts.

  • Scene lifecycle: enter(ctx) → update(ctx, dt) → render(ctx, alpha)
    → exit(ctx). Scenes can import from @engine/, @core/, @ui/,
    @content/. Never the other way around.

  • SceneContext services available: input, renderer, assets, audio,
    saveStore, worldClock, changeScene. Do not punch through to globals.

CONTENT FORMATS

  • Level format is .tmj.json (Tiled JSON with .json appended so Vite's
    native JSON handling works with zero config). NEVER bare .tmj.

  • Tile layer must be named "collision". Object layer must be named
    "objects". Object types used so far: "player_spawn", "exit".
    (Future: "hazard", "save_point", trigger volumes.)

  • Content JSON lives in src/content/. Gameplay code imports via
    @content/... — not via fs, not via fetch.

INPUT

  • Pause key is KeyP everywhere. Never F10 (browsers capture it).
  • ESC leaves the current sub-scene back to its parent (station → space,
    planet-surface → planet-landing, etc.).
  • Planet surface controls: A/D run, SPACE (or W) jump.
  • Space combat controls: arrow keys / WASD fly, SPACE fire, P pause.

COMMITS

  • Identity: `git -c user.email="dev@blackstar.local"
                  -c user.name="Black Star Dev" commit -m "..."`.
    Bot identity — no personal author, no Co-Authored-By trailers,
    no 🤖 Generated with Claude Code lines, no emojis.

  • No --no-verify. No --amend. If a hook fails, fix the cause and
    create a new commit.

  • Never stage .claude/settings.json in gameplay commits.

  • Conventional-commit style prefixes: feat / fix / refactor /
    content / test / docs / plan. Scope in parens: feat(planet): ...

    first-draft. Expect to tune them against the playthrough.

Three design-level decisions locked in during M3a:
  1. Collision is swept, X-axis then Y-axis independent. Point-probe
     at destination was the plan's original — it tunnelled through
     walls at any real velocity. Shipped code walks tile cells along
     the sweep path and stops at the first solid.
  2. Controller owns velocity every frame. Scene does
     `controller.vy = body.vy` before update, `body.vy = controller.vy`
     after. No Math.max / Math.min merging (the plan's original had
     Math.max which silently discarded mid-air jump impulses).
  3. Coyote and jump buffer timers are set-then-decrement in the same
     frame. Pressing jump mid-air shows jumpBufferSec − dt immediately.
     Feels tighter in hand and the test suite requires it.

Repository-level invariants still holding:
  • grep -rn "@engine\|@scenes\|@ui" src/core → empty
  • grep -rn "Math.random" src/core → empty (cosmetic uses are in
    src/engine/Camera.ts only)
  • No DungeonScene / DungeonGen / RoomDef / @content/rooms references
    anywhere in src or tests.

 9. KNOWN SHARP EDGES
================================================================================

  • SpaceScene is heavy (~450 lines, 5 entangled concerns). A
    CombatSystem extraction is queued but not scoped — defer until
    M3b sprite pass lands and makes the scene even heavier.

  • modules.json duplicates weapon tuning that weapons.json owns
    (damage + range live in both). Slot-fit lives in modules.json,
    behavior in weapons.json. Either drop the duplicates or accept the
    footgun. Flagged in M2c retro; not yet resolved.

  • availablePower is hardcoded to 100 in three call sites (SpaceScene
    player fire, enemy shooter fire twice). PowerBudget exists in core
    but isn't wired into canFire. M3b or M3c polish task.

  • Enemy spawns are hand-placed (4 fixed coordinates). No wave system,
    no Decay-Clock-driven spawning, no respawn. Kill all 4 and the
    sector is empty forever.

  • Player death → TitleScene. No "you died" screen, no legacy
    inheritance. Legacy is a planned milestone, not close.

  • Planet camera is a centered clamp with no lookahead, no smoothing,
    no deadzone. Fine for 640×360-sized rooms. Blocks anything larger.

  • Planet hazards, enemies, save points, and combat all don't exist
    yet. Planet surface is currently "walk around in one room, touch
    exit to leave." By design — M3a is foundation, M3b is content.
